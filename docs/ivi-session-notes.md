## TL;DR — The Winning Recipe

The Qwen3-TTS finetuning script (`finetuning/sft_12hz.py` upstream) has bugs, but the main issue for producing usable output on **0.6B-Base** is **learning rate**, not the bugs people have posted fixes for.

```bash
# On a 40GB+ GPU (A100 recommended) with the upstream script + ONE patch (text_projection wrap):
python3 finetuning/sft_12hz.py \
  --init_model_path /workspace/models/0.6B-Base \
  --output_model_path /workspace/output \
  --train_jsonl /workspace/training-data/train_with_codes.jsonl \
  --batch_size 2 \
  --lr 1e-7 \
  --num_epochs 2 \
  --speaker_name your_voice_name
```

- lr **1e-7** is critical (not 2e-6, not 2e-5).
- Gradient accumulation 4 (built into script). Effective batch = 8.
- **Epoch 1 checkpoint** is the pick. Epoch 0 is underfit, epoch 2+ can start drifting.
- The only script edit needed vs. upstream main: wrap `text_embedding` with `text_projection` on line 89 (fixes 0.6B dimension mismatch).
- **Do NOT** apply the "double label shift" fix or the "remove sub-codebook loop" fix at this LR — they either break training or require further compensating changes.

See [our GitHub comment](https://github.com/QwenLM/Qwen3-TTS/issues/39#issuecomment-4289306999) for the public data point.

## The Debugging Journey (what we tried and why each failed or worked)

| Run | Patches | LR | Epochs | Loss end | Result |
|---|---|---|---|---|---|
| v1 | text_projection | 2e-6 | 10 | ~3.0 | Epoch 0 usable (98% clean, slightly fast), epoch 1+ EOS broken |
| v2 | text_projection + remove sub-codebook loop | 2e-6 | killed | stuck ~12 | Model wouldn't learn at all |
| v3 | text_projection + remove double shift + explicit cross_entropy in modeling | 2e-5 | 20 | ~1.0 | "Aliens underwater" — classic overfitting |
| v4 | text_projection + shift fix | 2e-6 | 10 | ~2.5 | Same pattern as v1: ep0 ok, ep2+ broken |
| v5 | text_projection | **1e-7** | **2** | ~12.8 | **✅ Works.** All epochs clean. Epoch 1 is the pick. |
| v6 | text_projection | **1e-7** | **3** | ~13.2 | ✅ Also works; epoch 1 still best. Epoch 2 not notably better. |

### Key insights from this journey

1. **LR is the dominant knob.** Community-posted "fixes" (shift bug, sub-codebook loop) either break training or need careful compensation. Low LR sidesteps the whole mess.

2. **Loss decreasing ≠ good training.** v3 had loss 1.0 and sounded like noise; v5 has loss 12.8 and sounds natural. Low loss at higher LR = overfitting on misaligned targets.

3. **EOS-loss symptom is diagnostic.** If the model hits `max_new_tokens` on simple texts instead of terminating, training is damaged. You won't hear it in streaming mode — you'll hear it as "speech compressed into first 20%, rest is noise/garbage." Always test with PyTorch generation and print audio length.

4. **mlx-audio was never the bug.** Our earlier "the voice sounds garbled in mlx-audio" was actually a broken model — PyTorch showed the same garble. Establishing this ground truth (testing PyTorch inference on the instance itself) saved a lot of time.

5. **The speaker embedding mechanism is simple and correct.** `codec_embedding.weight[3000]` is written with the ref-audio-derived embedding (norm ~10). At inference, `voice="ivi_female"` → config maps to slot 3000 → embedding lookup → injection into codec sequence position 6. No mlx-audio-specific handling needed.

6. **Our training data is synthetic but works.** 385 clips voice-cloned from one Cartesia reference through the 1.7B model. No real recordings. Voice identity transfers cleanly.

### What we tried that DIDN'T work and why (bugs to avoid)

**Double label shift "fix" (PR #178 adjacent / fumyou13 issue #179):**
- Change: drop manual `[:, :-1]` / `[:, 1:]` in `sft_12hz.py` + replace `self.loss_function(...)` with explicit `F.cross_entropy(...)` in `qwen_tts/core/models/modeling_qwen3_tts.py`.
- Result: loss drops way too fast (13→3 in 100 steps, 13→1 over 20 epochs). Audio is unusable. Model overfits its tiny 385-clip dataset very quickly because each step is now "correctly" shifted and effective.
- If you try this fix, drop LR to 5e-8 or 1e-8 to compensate.

**Sub-codebook loop removal (PR #178):**
- Change: remove the `for i in range(1, 16):` block that feeds future codec layers into the AR model during training.
- Result: loss won't drop below ~12. Model can't learn because the leak was actually providing necessary training signal.
- Multiple independent forks (rekuenkdr, guybrush1984) tried this and reverted it. It's a real bug, but removing the leak breaks more than it fixes.

**Higher learning rates:**
- lr=2e-5 → EOS destroyed in epoch 0, all outputs garbage.
- lr=2e-6 → Epoch 0 usable, epoch 1+ EOS broken.
- lr=1e-7 → Stable across all tested epochs (0-2).

## Hard-Won Lessons (keep these in mind next session)

- **LR is the dominant knob.** Not loss, not epochs, not patches.
- **Verify with PyTorch inference on the GPU instance before anything else.** It's the ground truth. mlx-audio issues are separable from training issues.
- **EOS termination is the canary.** Any epoch that hits `max_new_tokens` on a 5-word sentence is a broken model. Don't waste time tweaking that checkpoint — retrain with lower LR.
- **Train with 1s trailing silence on clips** — community-confirmed (dariox1337) to reduce rushed-speech artifacts. Our data already has this.
- **Loss-decreasing-ness is not a quality signal.** Sometimes stopping earlier (when loss is STILL HIGH) produces better audio.
- **Don't destroy instances** — stop them. Let user decide when to clean up.
- **Save audio samples to `~/Downloads/<subfolder>/`, don't `afplay` inline.** User preference.
- **The Qwen3-TTS maintainers are unresponsive to community fixes.** Don't wait for upstream; apply the text_projection patch yourself and move on.

## v7 Multi-Voice Addendum (2026-04-21, evening session)

Successfully extended the single-voice recipe to train **Katie + Joe jointly** into one checkpoint with distinct slot assignments (Katie=3000, Joe=3001). Pipeline works. Quality is not yet production-grade.

### What changed in code vs v6

New script: **`sft_12hz_multivoice.py`** — adapts `sft_12hz_patched.py` with three targeted changes:

1. **`VoiceAwareDataset` subclass** wraps upstream `TTSDataset`. `__getitem__` injects `voice_name` from the JSONL entry; `collate_fn` pops it into a `voice_names` list carried through the batch.

2. **`target_speaker_embeddings` is now a dict** keyed by `voice_name` (was a single global tensor in v6). For each sample in each batch, first-seen speaker embedding is cached per voice. At checkpoint save, each voice's cached embedding is written to its own slot. `spk_id` and `spk_is_dialect` config maps are populated for all voices.

3. **Ref-mel padding fix (critical bug encountered)**. Upstream `TTSDataset.collate_fn` does `torch.cat(ref_mels, dim=0)`, which silently assumes all refs have identical shape. Fine for single-voice training (all samples share one ref.wav). Breaks for multi-voice: Katie's ref is 10s, Joe's is 7s → different T after mel-spec → `RuntimeError: Sizes of tensors must match`. Our wrapped collate pads each ref_mel to the batch's max T on **dim=1**, which is where T lives after upstream's `.transpose(1,2)` — ref_mel shape is `[1, T, 128]`, not `[1, 128, T]`. Took one debug cycle to get right (I padded dim=-1=128 first, which is the n_mels dim and identical across all refs, so nothing happened).

Training invocation:
```bash
python3 sft_12hz_multivoice.py \
```
